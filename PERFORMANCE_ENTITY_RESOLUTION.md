# Оптимизация классификатора и различия лёгких/сложных таблиц

Документ фиксирует причины медленной работы классификатора и подробно описывает,
чем отличается обработка лёгких таблиц (`mart.price_facts` / `mart.metrics`) от
сложных шихтовочных листов (домен `cells` / CellEngine).

## 1. Важное уточнение

Оптимизация относится не к самому CellEngine для сложных таблиц, а к **общему
шагу классификатора**, который выполняется *перед* тем, как система решает,
куда отправить запрос — на лёгкую или сложную таблицу. Ускорение затронуло
оба пути.

## 2. Как система разделяет лёгкие и сложные таблицы

| | Лёгкие таблицы | Сложные таблицы |
|---|---|---|
| Данные | `mart.price_facts` (цены: item / supplier / period / value) и `mart.metrics` (план/факт) | Листы **«2 блок»**, **«3 блок»**, **«Отклонения от БЮДЖЕТА и ПЛАНА»** — нерегулярная сетка ячеек |
| Тип вопросов | «цена/поставщик/период», агрегации AVG/MIN/MAX | A1-координаты (`C20`, `M61`), подписи («фактическая доля», «расход из силосов»), вычисления между ячейками |
| Обработчик | SQL-пайплайн: `classifier → disambiguation → planner → codegen → executor → verifier → answer` | **CellEngine**: `classifier → cell_engine → answer` (без генерации SQL) |
| Источник | Нормализованная long-витрина | Представление `mart.cells` + функция `a1_ref()` ([`cells_view.py`](../src/core/db/cells_view.py)) |

Ключевая развилка — в [`routing.py`](../src/services/agent/nodes/routing.py:26):
если классификатор поставил `Domain.CELLS` (детерминированный детектор
[`looks_like_cell_query`](../src/services/agent/nodes/classifier_node.py:166)),
запрос уходит сразу в CellEngine и **минует** SQL-генерацию по
`price_facts/metrics`. Подробно про сложные листы — в
[`FEATURES_COMPLEX_TABLES.md`](FEATURES_COMPLEX_TABLES.md).


## 3. Что именно изменено (в [`entity_resolver.py`](../src/services/entity_resolution/entity_resolver.py))

1. **Убран DB-скан из горячего пути.** Тяжёлый pg_trgm-запрос по всей
   `price_facts` больше не выполняется на каждый вопрос.
2. **Ленивый in-memory каталог сущностей.** Один лёгкий `SELECT DISTINCT
   item_name / supplier` из `mart.price_facts` (маленький результат — только
   уникальные значения) грузится раз в **TTL = 60 сек**
   (`CATALOG_TTL_SECONDS`), затем сущности лежат в памяти процесса.
3. **Скоринг в Python.** Вопрос токенизируется (`_extract_tokens`), стоп-слова
   и агрегатные термины («минимальная», «месяцы», «цена»…) отбрасываются через
   `_STOPWORDS`; схожесть сущностей считается через `difflib.SequenceMatcher` +
   substring-правила. Например, «Какова была минимальная цена на цинковый
   лом…» → токены `цинковый, лом` → мгновенное сопоставление из кэша.
4. **API сохранён.** `resolve_candidates`, `index_entities`,
   `entities_for_prompt`, `EntityCandidate.to_dict` не изменились — оба
   потребителя ([`classifier_node.py`](../src/services/agent/nodes/classifier_node.py:98)
   и [`entity_resolution_node.py`](../src/services/agent/nodes/entity_resolution_node.py:27))
   работают без правок.

## 5. Как фикс влияет на каждый путь

- **Лёгкий запрос** (цена/метрика): классификатор быстро получает кандидатов
  item/supplier из кэша, дальше planner/codegen генерируют SQL по
  `price_facts/metrics`. Время классификатора перестало зависеть от размера
  факт-таблицы.
- **Сложный запрос** (домен `cells`): логика не тронута — `looks_like_cell_query`
  по-прежнему ставит `Domain.CELLS`, routing направляет в CellEngine. Изменилась
  только скорость самого шага классификатора: раньше он тащил на себе ненужное
  сканирование `price_facts` ради сущностей, которые для cell-вопросов почти не
  используются; теперь этот шаг мгновенный.

## 6. Что НЕ менялось

- Пайплайн `mart.price_facts` и `mart.metrics` работает как раньше.
- Детекция cell-запросов, маршрутизация в CellEngine и доступ к `mart.cells` —
  без изменений.
- Компилятор SQL по-прежнему read-only с белым списком таблиц.
- Тесты `test_classifier_domain`, `test_cells_domain`, `test_sql_compiler` не
  затронуты (зависят от `_heuristic_domain`/детекции, а не от pg_trgm).

## 7. Итог

Медленный классификатор был общим узким местом, которое тормозило оба маршрута.
Исправление локализовано в `entity_resolver` и убирает дорогое сканирование
`price_facts` из каждого запроса, не затрагивая саму логику обработки сложных
таблиц.
